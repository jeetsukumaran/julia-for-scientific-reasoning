Author

1 Installing Julia

Proficiencies
  • Distinguishing Julia, the julia command, and the juliaup version manager.
  • Installing the current stable Julia release on Windows, macOS, or Linux.
  • Confirming that the shell can find and start Julia.
  • Identifying the installed Julia version and the executable selected by the shell.
  • Updating Julia with juliaup.
  • Recognizing common installation and PATH problems.

Installing Julia means placing a Julia runtime on the computer and making the command julia available to the shell. The recommended installer is juliaup, the Julia version manager maintained by the Julia project. It installs Julia, adds the launcher to the shell’s PATH, and provides commands for installing and updating Julia versions.

The installation has 3 related pieces:

Piece Role Typical command
Julia runtime Compiles and evaluates Julia code. Started through julia.
julia launcher Selects a Julia version and starts it. julia or julia --version
juliaup Installs, selects, updates, and removes Julia versions. juliaup status or juliaup update

For ordinary use, the distinction is simple: use julia to run Julia, and use juliaup to manage the Julia installation.

1.1 The recommended installation

The Julia project recommends installing the latest stable release through juliaup. The stable release is represented by the release channel. When that channel is updated, juliaup installs the newest stable patch release without requiring a new installation procedure.

TipUse the stable release

Use the release channel for this course unless an exercise specifies another version. The lts channel provides the long-term support release, while beta, rc, and nightly provide prerelease or development versions. Prerelease versions are intended for testing Julia itself and may not work with every package used in the course.

If Julia was installed previously by another method, first identify the version and executable that the shell currently finds:

$ julia --version
$ which julia

In PowerShell, use:

PS> julia --version
PS> Get-Command julia

An older installation can coexist with juliaup, but 2 different julia commands on the PATH make it unclear which installation will start. The juliaup documentation recommends removing earlier Julia installations and their manually added PATH entries before installing through juliaup. Use the earlier installation’s documented uninstaller, or ask for assistance if the computer is managed by an institution.

1.2 Installing on Windows

Open Windows Terminal, PowerShell, or Command Prompt. Install Julia from the Microsoft Store source with winget:

PS> winget install --name Julia --id 9NJNWW8PVKMN -e -s msstore

This installs juliaup and the current stable Julia release. When installation finishes, close the terminal and open a new one so that the new shell receives the updated PATH.

If winget or the Microsoft Store is unavailable, open the official Julia installation page and use its MSIX App Installer option. On a managed computer, installation may be restricted by institutional policy; in that case, contact the system administrator rather than substituting an unofficial download.

NoteWindows Start menu and terminal access

The Windows installation also provides a Start menu entry and a Windows Terminal profile. This course uses the julia shell command because the same command works on Windows, macOS, and Linux and makes the selected Julia version explicit.

1.3 Installing on macOS and Linux

Open a terminal and run the installer command published by the Julia project:

$ curl -fsSL https://install.julialang.org | sh

The command downloads the installer from install.julialang.org and passes it to the shell. Read the displayed installation summary, accept the defaults, and allow the installer to add Julia to the PATH. The default installation belongs to the current user and normally does not require sudo or administrator access.

When installation finishes, close the terminal and open a new one. This starts a new shell that reads the configuration updated by the installer. If the installer prints a different command for refreshing the current shell, that command can be used instead.

ImportantRun installers only from the official domain

The command above executes code downloaded from the network. Type it only after confirming that the address is exactly https://install.julialang.org, or copy the current command from the official Julia installation page.

Do not install the Julia runtime from a Linux distribution’s package repository for this course. Distribution packages can be older than the supported Julia release or can differ from the official binaries. Use juliaup, or use an official manual binary when juliaup is not available.

1.4 Verifying the installation

Open a new shell and ask Julia to report its version:

$ julia --version
julia version 1.12.7

The exact version changes as Julia releases are published. The important result is a version line rather than a command not found error.

Next, inspect the version selected by juliaup:

$ juliaup status

The status output lists installed channels, their Julia versions, and the default channel. For a new course installation, release should be installed and selected as the default.

Confirm which executable the shell found:

$ which julia

In PowerShell, use:

PS> Get-Command julia

Finally, start Julia:

$ julia

At the julia> prompt, evaluate a small expression and inspect the runtime:

julia> 2 + 2
4

julia> VERSION
v"1.12.7"

julia> Sys.KERNEL
:Linux

julia> Sys.ARCH
:x86_64

julia> exit()

Sys.KERNEL and Sys.ARCH report the operating system kernel and processor architecture. Their values will differ on Windows, macOS, and computers with ARM processors. The final call, exit(), ends Julia and returns to the shell. The next lesson examines this interactive julia> prompt, called the Julia read-eval-print loop (REPL), in detail.

1.5 Juliaup channels and versions

A juliaup channel is a named pointer to a Julia release or series of releases. The channel determines which runtime the julia launcher starts.

Channel form Meaning Example launch command
release Latest stable Julia release. julia +release
lts Latest long-term support release. julia +lts
1.12 Latest installed patch release in the Julia 1.12 series. julia +1.12
1.12.7 One exact Julia release. julia +1.12.7

The plain command julia starts the default channel. The +channel selector starts another installed channel for that command only. For example:

$ juliaup add lts
$ julia +lts --version
$ julia +release --version

Adding a channel does not change the default. To select the stable release as the default explicitly, run:

$ juliaup default release

List installed channels with juliaup status and all available channels with juliaup list. Most learners need only the default release channel. Multiple channels become useful when a project requires an older Julia series or when code must be tested against more than 1 Julia version.

1.6 Updating Julia

Update every installed channel with:

$ juliaup update

Or update only the stable channel with:

$ juliaup update release

The update affects Julia processes started afterward; it does not replace the runtime inside a Julia process that is already running. Run julia --version after the update to confirm the selected version.

Updating Julia and updating Julia packages are separate operations. juliaup update updates Julia runtimes. Julia’s package manager updates packages inside an environment, as described later in this chapter.

1.7 Manual installation as a fallback

juliaup is the standard installation path, but some managed, offline, or unusual systems cannot use it. The Julia project provides manual downloads of official binaries for those cases.

A manual installation requires more decisions:

  • selecting the correct operating system and processor architecture
  • placing or unpacking the downloaded application
  • adding its bin directory to the shell PATH
  • downloading and installing later Julia releases manually

Use a manual binary only when juliaup is unavailable or a specific deployment requires it. Follow the official platform-specific instructions rather than instructions for an unofficial package or mirror.

Installing Julia does not install external Julia packages such as DataFrames or CairoMakie. Those packages belong to Julia environments and are installed by Julia’s package manager. The later lesson on environments, projects, and package management introduces that process.

1.8 Common installation problems

Symptom Likely cause First check
julia: command not found or “julia is not recognized” The current shell has not read the updated PATH, or installation did not finish. Close every terminal window, open a new one, and run julia --version.
juliaup works but julia does not The Julia launcher directory is not available on PATH. Reopen the shell, then review the final message printed by the installer.
julia --version reports an unexpected older release Another Julia executable appears earlier on PATH. Run which julia on macOS/Linux or Get-Command julia -All in PowerShell.
winget cannot access the Store source The Microsoft Store is disabled, unavailable, or blocked by policy. Use the official MSIX App Installer link or contact the system administrator.
The macOS/Linux installer cannot download Julia The network, proxy, or firewall blocks an official Julia domain. Confirm network access to julialang.org and julialang-s3.julialang.org.
Julia starts, but the first package operation takes a long time Packages and compiled caches are being downloaded or generated. Let the operation finish; this is separate from installing the runtime.
VS Code cannot find Julia VS Code was already running when Julia changed the PATH, or the Julia extension is not installed. Restart VS Code, then confirm julia --version in its integrated terminal.

Do not repeatedly install Julia through different methods to solve a PATH problem. First locate the executable selected by the shell, then correct or remove the conflicting installation.

2 Executing Julia programs: the Julia runtime, REPL, and program files

Proficiencies
  • Starting Julia from a shell.
  • Distinguishing shell commands from Julia expressions.
  • Using the Julia read-eval-print loop (REPL) for interactive work.
  • Running a Julia source file as a program.
  • Understanding what a .jl file is.
  • Understanding what println does in a script.
  • Passing command-line arguments to a Julia program.
  • Reading command-line arguments with ARGS.
  • Understanding the role of PROGRAM_FILE.
  • Using include to evaluate one Julia file from another Julia session or file.
  • Using @main or main(ARGS) to define a script entry point.
  • Running Julia with a project environment using --project.
  • Choosing between REPL execution and fresh-process execution in VS Code.

Executing a Julia program means starting a Julia process and asking it to evaluate Julia code. That code may come from the keyboard, from a file, from a short expression passed on the command line, or from a file that another Julia file includes. The syntax and experience differ across these cases, but the same Julia language is being evaluated.

We typically use a a shell command to invoke the Julia program to evaluate Julia code or expressions, either typed directly or sourced from a file.

  • A shell command is typed at the operating-system command prompt.
  • A Julia expression is typed at the julia> prompt or written inside a .jl file.

For example, this is a shell command to have Julia execute the contents of the file hello.jl:

$ julia hello.jl

This is Julia code:

println("Hello from Julia.")

This distinction removes many early confusions. The command julia hello.jl starts Julia. The expression println("Hello from Julia.") is code that Julia evaluates.

NotePrompt markers are not part of the command

In examples, $, julia>, pkg>, help?>, and shell> identify where text is typed. Type julia hello.jl, not $ julia hello.jl. Type println("Hello from Julia."), not julia> println("Hello from Julia.").

Concept Meaning Example
Shell The program where operating-system commands are typed. bash, zsh, PowerShell, or the VS Code integrated terminal.
Julia executable The program named julia that starts the Julia runtime. julia --version
Julia process One running instance of Julia. A REPL session or one run of julia hello.jl.
Source file A text file containing Julia code. hello.jl
Working directory The directory Julia uses as the starting point for relative paths. The result of pwd() inside Julia.

When the shell receives this command,

$ julia hello.jl

the operating system starts the julia executable. Julia initializes a new process, reads the file hello.jl, evaluates the expressions in that file, prints whatever the program explicitly prints, and then exits.

When the shell receives this command,

$ julia

the operating system starts the same julia executable, but Julia enters an interactive session instead of reading a program file. That interactive session is the REPL.

2.1 The Julia runtime

The Julia runtime is the running Julia system. It includes the language evaluator, compiler, standard library, package-loading machinery, memory management, and the process that executes the code. For beginner purposes, the runtime is what starts when the julia command works.

The simplest runtime check is:

$ julia --version
julia version 1.12.6

The exact version number may differ on another machine. The useful point is that the shell found a program named julia, started it, and Julia printed version information.

The common execution forms are:

$ julia
$ julia hello.jl
$ julia -e 'println(2 + 2)'
$ julia --project=. analysis.jl

Each form starts Julia, but each form gives Julia a different job.

Command What Julia does
julia Start an interactive REPL.
julia hello.jl Evaluate the file hello.jl, then exit.
julia -e 'println(2 + 2)' Evaluate the expression provided on the command line, then exit.
julia --project=. analysis.jl Activate the project in the current directory, evaluate analysis.jl, then exit.

The runtime also has startup options. The options that beginners most often see are:

Option Meaning
--version Print the installed Julia version.
--help Print command-line help.
--project=. Use the current directory as the active Julia project.
--project=@. Search upward from the current directory for a Julia project.
-e 'expression' Evaluate a short Julia expression.
-i Remain interactive after evaluating a file or expression.

The --project option matters once a program uses external packages. For a small file that only uses Julia’s standard functionality, julia hello.jl is enough. For a course exercise or research project with a Project.toml, use the project environment explicitly:

$ julia --project=. analysis.jl

This tells Julia which package environment to use before it evaluates the program.

2.2 The Julia REPL

REPL stands for read-eval-print loop. The REPL reads an expression, evaluates it, prints the result, and then loops back for the next expression. It is Julia’s interactive workbench.

Start it from a shell:

$ julia

Julia prints a banner and gives a prompt:

julia>

At that prompt, type Julia expressions:

julia> 2 + 3
5

julia> sqrt(16)
4.0

The REPL is useful for small experiments. It is also useful for learning because feedback is immediate. If an expression is complete, Julia evaluates it as soon as Enter is pressed. If an expression is incomplete, Julia waits for more input:

julia> function double(x)
           return 2x
       end
double (generic function with 1 method)

julia> double(10)
20

The REPL prints returned values. A script does not automatically print returned values. This is an important difference.

Consider this file:

# quiet.jl
2 + 2

Running it as a script produces no visible output:

$ julia quiet.jl

The expression was evaluated, but nothing printed it. For visible output in a script, call println, print, show, display, or another output function:

# visible.jl
println(2 + 2)

Now the script prints:

$ julia visible.jl
4

The REPL stores the value of the most recent expression in ans:

julia> 40 + 2
42

julia> ans * 10
420

Use ans only for quick interactive work. Program files should use named variables instead.

2.2.1 REPL modes

The Julia REPL has several modes. The prompt changes to show the current mode.

Mode How to enter Prompt Purpose
Julia mode Default mode julia> Evaluate Julia expressions.
Help mode Type ? at an empty prompt help?> Search documentation.
Package mode Type ] at an empty prompt pkg> Manage packages and environments.
Shell mode Type ; at an empty prompt shell> Run shell commands from inside Julia.

Press Backspace at an empty mode prompt to return to Julia mode.

Help mode is especially valuable for beginners:

julia> ?
help?> println

Package mode is used later when adding and managing packages:

julia> ]
pkg> status

Shell mode is useful for quick directory checks:

julia> ;
shell> pwd

The shell mode is still shell syntax, not Julia syntax. The prompt helps keep the two languages separate.

2.2.2 The REPL working directory

The REPL has a working directory. Julia uses this directory as the starting point for relative file paths.

Check it with:

julia> pwd()
"/home/student/julia-practice"

Change it with:

julia> cd("projects")

List files with:

julia> readdir()

The shell has a working directory too. When Julia starts from a shell, Julia usually inherits the shell’s working directory. This means the following 2 workflows usually begin in the same directory:

$ pwd
/home/student/julia-practice
$ julia
julia> pwd()
"/home/student/julia-practice"

When a file cannot be found, check the working directory first.

2.2.3 Exiting the REPL

Exit the REPL with either:

julia> exit()

or press Ctrl-D at an empty julia> prompt.

Use Ctrl-C to interrupt code that is currently running. Use Ctrl-D to end the REPL session.

2.3 Julia program files

A Julia program file is a plain-text file containing Julia code. By convention, Julia source files end in .jl.

Examples:

hello.jl
analysis.jl
simulate_population.jl
plot_results.jl

The file extension does not make the code special by itself. It tells people and tools that the file contains Julia source code. When the command julia hello.jl runs, Julia reads and evaluates the file.

2.3.1 A first script

Create a file named hello.jl:

message = "Hello from a Julia file."
println(message)

Run it from the shell:

$ julia hello.jl
Hello from a Julia file.

The program has 2 expressions. The first expression creates a variable named message. The second expression prints the value stored in message.

Julia evaluates a script from top to bottom. Later expressions can use names created by earlier expressions:

radius = 3.0
area = pi * radius^2

println("radius = ", radius)
println("area = ", area)

Save that as circle_area.jl and run it:

$ julia circle_area.jl
radius = 3.0
area = 28.274333882308138

This is already a complete program. It receives no user input and uses no packages, but it executes reproducibly from a file.

2.3.2 Script output

Output is explicit. The expression area = pi * radius^2 computes and stores a value, but it does not print anything. The function println writes text to standard output, which is usually the terminal.

Use println when each output should end with a newline:

println("first line")
println("second line")

Use print when output should not automatically end with a newline:

print("radius = ")
println(radius)

For beginner scripts, println is usually the right output function.

2.3.3 Running a file by path

The file does not have to be in the current directory if the shell command gives a path to it:

$ julia scripts/hello.jl

That command asks Julia to evaluate the file hello.jl inside the scripts directory.

Relative paths start from the current working directory:

$ julia scripts/hello.jl

Absolute paths start from the root of the file system:

$ julia /home/student/julia-practice/scripts/hello.jl

Relative paths are shorter. Absolute paths are less sensitive to the current working directory.

2.3.4 The script file and the working directory

A beginner script often needs to read a data file. This is where a subtle distinction matters.

The script file has a location:

/home/student/project/scripts/analyze.jl

The Julia process also has a working directory:

/home/student/project

These are related, but they are not the same concept. When code reads a relative path such as "data/observations.csv", Julia resolves that path relative to the process working directory.

For project scripts, it is often more stable to build paths relative to the script file:

script_dir = @__DIR__
data_path = joinpath(script_dir, "..", "data", "observations.csv")

@__DIR__ expands to the directory that contains the current source file. joinpath builds a path using the conventions of the operating system. This avoids hard-coding path separators such as / or \.

2.3.5 Command-line arguments

Programs often need input from the command line. In Julia, command-line arguments passed to a script are available in the global constant ARGS.

Create show_args.jl:

println("PROGRAM_FILE = ", PROGRAM_FILE)
println("ARGS = ", ARGS)

Run it with extra words after the script name:

$ julia show_args.jl oak maple pine
PROGRAM_FILE = show_args.jl
ARGS = ["oak", "maple", "pine"]

PROGRAM_FILE stores the script file name or path. ARGS stores the arguments that came after the script name. The values in ARGS are strings.

This matters when the program expects a number:

radius_text = ARGS[1]
radius = parse(Float64, radius_text)

println(pi * radius^2)

Run it with:

$ julia circle_from_args.jl 3.0
28.274333882308138

The argument 3.0 begins as the string "3.0". The function parse(Float64, radius_text) converts that string to a Float64.

2.3.6 Julia options and program arguments

Julia command-line options come before the program file. Program arguments come after the program file.

$ julia --project=. circle_from_args.jl 3.0

In that command:

  • --project=. is an option for Julia.
  • circle_from_args.jl is the program file.
  • 3.0 is an argument for the program.

Use -- when it helps separate Julia options from the program file and program arguments:

$ julia --project=. -- circle_from_args.jl 3.0

The delimiter is especially useful when a program argument itself starts with -:

$ julia --project=. -- report.jl --format=csv

In that command, --format=csv belongs to report.jl, not to Julia.

2.3.7 A script with functions

Short scripts can be written as top-level expressions. As soon as a script contains reusable logic, put that logic into functions.

This script separates calculation, formatting, and command-line execution:

function parse_radius(text::AbstractString)::Float64
    radius = parse(Float64, text)
    radius >= 0 || throw(ArgumentError("Expected a non-negative radius. Received $(radius)."))
    return radius
end

function circle_area(radius::Real)::Float64
    return pi * Float64(radius)^2
end

function circle_report(radius::Real)::String
    area = circle_area(radius)
    return "A circle with radius $(radius) has area $(area)."
end

radius = parse_radius(ARGS[1])
println(circle_report(radius))

Save it as circle_report.jl and run:

$ julia circle_report.jl 3.0
A circle with radius 3.0 has area 28.274333882308138.

This style is easier to test and revise than a long file of top-level statements. The functions perform the reusable work. The final lines connect those functions to command-line execution.

2.3.8 A script entry point with main

The previous script still has executable top-level code at the bottom. For larger scripts, define a main function and make the bottom of the file a small entry point.

function parse_radius(text::AbstractString)::Float64
    radius = parse(Float64, text)
    radius >= 0 || throw(ArgumentError("Expected a non-negative radius. Received $(radius)."))
    return radius
end

function circle_area(radius::Real)::Float64
    return pi * Float64(radius)^2
end

function circle_report(radius::Real)::String
    area = circle_area(radius)
    return "A circle with radius $(radius) has area $(area)."
end

function main(args::AbstractVector{<:AbstractString})::Int
    length(args) == 1 || throw(ArgumentError("Usage: julia circle_main.jl RADIUS"))

    radius = parse_radius(only(args))
    println(circle_report(radius))

    return 0
end

exit(main(ARGS))

Save it as circle_main.jl. Run it the same way:

$ julia circle_main.jl 3.0
A circle with radius 3.0 has area 28.274333882308138.

The function main receives ARGS. It returns an integer exit code. By convention, exit code 0 means success. A nonzero exit code means failure.

The line exit(main(ARGS)) is the explicit script entry point. It says: run main with the command-line arguments, then use the returned integer as the process exit code.

2.3.9 A script entry point with @main

Julia 1.11 added @main as an opt-in entry-point mechanism for scripts. On Julia 1.11 or newer, the previous script can end by defining (@main)(args):

function parse_radius(text::AbstractString)::Float64
    radius = parse(Float64, text)
    radius >= 0 || throw(ArgumentError("Expected a non-negative radius. Received $(radius)."))
    return radius
end

function circle_area(radius::Real)::Float64
    return pi * Float64(radius)^2
end

function circle_report(radius::Real)::String
    area = circle_area(radius)
    return "A circle with radius $(radius) has area $(area)."
end

function (@main)(args::AbstractVector{<:AbstractString})::Int
    length(args) == 1 || throw(ArgumentError("Usage: julia circle_main.jl RADIUS"))

    radius = parse_radius(only(args))
    println(circle_report(radius))

    return 0
end

Run it as a script:

$ julia circle_main.jl 3.0
A circle with radius 3.0 has area 28.274333882308138.

The @main form tells Julia to call Main.main(ARGS) after the script finishes loading. This makes the script entry point explicit while keeping the file clean.

For Julia versions older than 1.11, use the explicit exit(main(ARGS)) form.

2.3.10 Top-level code and reusable code

A useful beginner rule is:

  • Use top-level code for small experiments and short throwaway scripts.
  • Use functions for calculations that have names, inputs, and outputs.
  • Use main(args) when a file is intended to be run as a command-line program.
  • Keep file reading, printing, and command-line parsing near the entry point.
  • Keep scientific calculations in functions that receive inputs and return values.

This separation makes the program easier to test. For example, circle_area(3.0) can be tested directly in the REPL. The script entry point can remain responsible for reading ARGS and printing results.

2.3.11 Evaluating a file with include

Running a file from the shell starts a fresh Julia process:

$ julia circle_main.jl 3.0

Evaluating a file with include happens inside an existing Julia process:

julia> include("circle_report.jl")

This distinction matters. When a file is run from the shell, Julia starts clean, evaluates the file, and exits. When a file is included in the REPL, definitions remain available afterward:

julia> include("geometry.jl")
circle_report (generic function with 1 method)

julia> circle_report(3.0)
"A circle with radius 3.0 has area 28.274333882308138."

include is also how one Julia file can evaluate another Julia file.

Create geometry.jl:

function circle_area(radius::Real)::Float64
    return pi * Float64(radius)^2
end

function circle_report(radius::Real)::String
    area = circle_area(radius)
    return "A circle with radius $(radius) has area $(area)."
end

Create run_geometry.jl in the same directory:

include("geometry.jl")

println(circle_report(3.0))

Run:

$ julia run_geometry.jl
A circle with radius 3.0 has area 28.274333882308138.

The call include("geometry.jl") evaluates the contents of geometry.jl. After that, run_geometry.jl can call circle_report.

include is simple and direct. It is appropriate for splitting one program across a few files. Packages use a more formal version of this idea, organized around modules and project environments.

2.3.12 include and repeated evaluation

Calling include("geometry.jl") more than once evaluates the file more than once. This is useful during learning:

julia> include("geometry.jl")

julia> circle_area(3.0)
28.274333882308138

Edit the file, save it, and include it again:

julia> include("geometry.jl")

The REPL now has the new definitions. This workflow is convenient, but remember that the REPL session keeps old variables and loaded packages until it exits. When behavior seems confusing, restart Julia or run the script in a fresh process.

2.3.13 include, using, and import

Julia has 2 broad ways to load code:

Mechanism Example Purpose
Code inclusion include("geometry.jl") Evaluate another source file as part of the current program.
Package loading using Statistics or import Statistics Load a package or standard library available in the active environment.

Use include for files that are part of the same program. Use using or import for packages.

For example:

using Statistics: mean

values = [1.0, 2.0, 3.0]
println(mean(values))

Statistics is a standard library. The statement using Statistics: mean makes the function mean available in the program.

For external packages, Julia must find the package in the active environment. That is why project activation matters:

$ julia --project=. analysis.jl

The next lesson introduces environments, packages, and projects in more detail.

2.3.14 A beginner execution checklist

When a Julia program does not run as expected, inspect these points in order:

  1. Confirm that the shell can find Julia.

    $ julia --version

  2. Confirm that the shell is in the intended directory.

    $ pwd
$ ls

  3. Confirm that the program file exists at the path passed to Julia.

    $ julia scripts/hello.jl

  4. Confirm that the program prints output explicitly.

    println("The program reached this line.")

  5. Confirm that command-line arguments are present before indexing ARGS.

    length(ARGS) == 1 || throw(ArgumentError("Usage: julia script.jl VALUE"))

  6. Confirm that the correct project environment is active when packages are used.

    $ julia --project=. analysis.jl

  7. Restart Julia or run in a fresh process if REPL state may be interfering.

    $ julia analysis.jl

2.3.15 Common error messages

Symptom Likely cause First check
julia: command not found Julia is not installed or not on the shell PATH. Run julia --version; revisit installation.
SystemError: opening file ... No such file or directory The file path is wrong relative to the working directory. Check pwd() in Julia or pwd in the shell.
BoundsError involving ARGS[1] The script expected an argument but none was supplied. Run julia script.jl value.
ArgumentError from parse A command-line argument could not be converted to the requested type. Print ARGS and inspect the actual strings.
UndefVarError A name was used before it was defined or loaded. Check spelling, evaluation order, and include calls.
ArgumentError: Package ... not found The package is not available in the active environment. Start Julia with --project=. or activate the right environment.
A changed file seems ignored The current REPL process still has older state or the edited file was not included again. Re-run include, restart the REPL, or run a fresh process.

Errors are information. Read the first line to identify the error type, then read the stack trace from the topmost line that points into the file being edited.

3 The VS Code development environment

3.1 Writing Julia programs

VS Code is an editor and development environment. It is not Julia itself. The Julia extension connects VS Code to a Julia installation and provides editor features such as syntax highlighting, code execution commands, an integrated REPL, inline results, plots, documentation lookup, and environment selection.

The usual beginner setup has 3 pieces:

  1. Julia is installed.
  2. VS Code is installed.
  3. The Julia VS Code extension is installed.

Open the course or project folder in VS Code before writing code. This gives VS Code a workspace folder. The workspace folder usually becomes the working directory for integrated Julia workflows.

Create Julia files with the .jl extension:

hello.jl
circle_report.jl
analysis.jl

A good beginner habit is to keep one clear entry-point file for each exercise. For example:

exercise-01/
  Project.toml
  hello.jl

or:

population-model/
  Project.toml
  src/
    model.jl
  scripts/
    run_model.jl

For small exercises, one .jl file is enough. For larger projects, place reusable calculations in separate files and keep the script entry point small.

3.2 Executing Julia code and programs

VS Code offers more than one execution path. The difference between them is not cosmetic. They create different execution conditions.

VS Code action Execution condition Use when
Execute code in REPL Sends selected code or the current top-level block to the integrated Julia REPL. Experimenting with a function or expression.
Execute file in REPL Evaluates the active file inside the integrated Julia REPL. Iterating quickly while keeping a session open.
Run file in new process Starts a new Julia process and runs the active file. Checking that a script works from a clean start.
Start without debugging Starts a new Julia process according to the launch configuration. Running a configured entry-point script with chosen arguments, working directory, and environment.

The integrated REPL is persistent. Values and definitions remain until the REPL exits. This is useful while exploring, but it can hide missing code or stale state.

A fresh process is stricter. It starts Julia from scratch, evaluates the file, and exits. If the file only works in the REPL but fails in a fresh process, the file probably depends on something that was created interactively but not written into the program.

For serious checks, run the file in a fresh process. For exploration, use the REPL.

3.2.1 The command palette

Most Julia extension commands are available from the VS Code command palette:

Ctrl-Shift-P

or on macOS:

Cmd-Shift-P

Search for commands beginning with Julia:. Important beginner commands include:

  • Julia: Start REPL
  • Julia: Execute Code in REPL
  • Julia: Execute File in REPL
  • Julia: Run File in New Process
  • Julia: Change Current Environment

Keyboard shortcuts can differ by platform and configuration. The command palette is the reliable way to find the command by name.

3.3 Running Julia code and programs in the integrated terminal

The VS Code integrated terminal is a shell inside the editor. Commands typed there are shell commands. This is often the clearest way to learn execution because it exposes the same command-line behavior used outside VS Code.

Open the integrated terminal and run:

$ julia --version

Run a file:

$ julia hello.jl

Run a file with a project environment:

$ julia --project=. analysis.jl

Run a file with arguments:

$ julia circle_main.jl 3.0

Start the REPL in the integrated terminal:

$ julia

Then evaluate a file from the REPL:

julia> include("hello.jl")

The integrated terminal is useful because the command is visible and repeatable. If a VS Code button behaves unexpectedly, run the corresponding shell command directly.

3.4 A recommended beginner workflow

Use this workflow until the execution model feels natural.

  1. Open the project folder in VS Code.
  2. Open the integrated terminal.
  3. Run julia --version to confirm that Julia is available.
  4. Create a small .jl file.
  5. Run it with julia file_name.jl.
  6. If the file uses packages, run it with julia --project=. file_name.jl.
  7. Use the REPL for experiments.
  8. Move working ideas from the REPL into the .jl file.
  9. Run the .jl file in a fresh process before considering it finished.

This workflow keeps exploration and reproducibility connected. The REPL supports discovery. The program file records the result. The fresh-process run proves that the file contains everything needed to execute.

4 Working with Julia: environments, projects, and package management

Proficiencies

  • Explaining what a Julia environment is, and what Project.toml and Manifest.toml each record.
  • Identifying which environment is active in a Julia session, from the pkg> prompt or with Pkg.status().
  • Installing packages into the default global environment with Pkg.add.
  • Creating and activating a project-specific environment with Pkg.activate.
  • Explaining why Manifest.toml, not Project.toml, is what makes an environment reproducible.
  • Reproducing a project’s exact package versions elsewhere with Pkg.instantiate.
  • Choosing between a global-environment workflow and a project-based workflow for a given task, and explaining why.

Every Julia session loads packages from somewhere. That “somewhere” is called an environment, and every Julia session has one active, whether or not it is ever mentioned explicitly. What follows first explains what an environment is — this part is identical no matter how it is used — and then compares 2 common ways of using that same mechanism: a single shared environment, and a dedicated environment per project.

4.1 What a package is

A Julia package is a body of Julia code, distributed with a name and a version, that can be loaded with using or import. DataFrames, CSV, and CairoMakie are packages. Julia also ships with standard-library packages, such as Statistics and Random, that are always available without an installation step. External packages are not automatically available; they must be installed into an environment first.

4.2 What an environment is

A Julia environment is a set of packages, at specific versions, that a Julia session can load. Concretely, an environment is a pair of files:

File Records
Project.toml The packages an environment directly depends on, and any version constraints on them.
Manifest.toml The complete, resolved set of packages needed to satisfy those dependencies — direct and indirect — each pinned to one exact installed version.

Project.toml is written and read by both people and Pkg. Manifest.toml is generated by Pkg and is not meant to be hand-edited.

NoteManifest.toml is machine-generated

Every Manifest.toml begins with the line # This file is machine-generated - editing it directly is not advised. Treat it as an output to inspect, not as a file to compose by hand.

At any moment, exactly one environment is the active project. Pkg.add, Pkg.status, and plain using/import all act on whichever environment is currently active. Nothing about this mechanism differs between “the global environment” and “a project environment” — a global environment is simply the environment that happens to be active by default.

4.2.1 The default global environment

Start Julia with no options, and the active project is a global environment tied to the installed Julia version:

julia> Base.active_project()
"/home/student/.julia/environments/v1.12/Project.toml"

This environment lives inside the Julia depot (~/.julia by default) and is shared by every Julia session started without --project. It is created automatically the first time it is needed and persists across sessions. The exact path differs by machine and Julia version.

Installing a package here needs no prior setup:

julia> using Pkg

julia> Pkg.add("DataFrames")

Check what is installed in the active project with Pkg.status:

julia> Pkg.status()
Status `~/.julia/environments/v1.12/Project.toml`
  [a93c6f00] DataFrames v1.8.2

The version shown will differ over time, as DataFrames releases new versions.

4.2.2 Project environments

A project environment is the same kind of Project.toml/Manifest.toml pair, kept in a project’s own directory instead of the depot. Activate one with Pkg.activate:

julia> using Pkg

julia> Pkg.activate(".")
  Activating new project at `/home/student/population-model`

Pkg.activate(".") by itself writes nothing to disk. Project.toml and Manifest.toml appear only once a package is actually added:

julia> Pkg.add("DataFrames")
   Resolving package versions...
    Updating `~/population-model/Project.toml`
  [a93c6f00] + DataFrames v1.8.2
    Updating `~/population-model/Manifest.toml`
  [a93c6f00] + DataFrames v1.8.2
  ...

From the shell, the same project can be made active for an entire run without touching code, using the --project option introduced in the previous lesson:

$ julia --project=. run_model.jl
TipReading the active environment off the pkg> prompt

The Pkg REPL-mode prompt names the active project. For the default global environment, it looks like:

(@v1.12) pkg>

For a project directory named population-model with no name field in its Project.toml, it looks like:

(population-model) pkg>

If add or status reports unexpected package versions, checking this prompt is the fastest way to confirm which environment is actually active.

4.2.3 Reproducing a project environment

Manifest.toml is what makes a project reproducible. Given both files, another machine — or the same machine after packages were never downloaded there — can recreate the identical set of package versions:

$ julia --project=. -e 'using Pkg; Pkg.instantiate()'

Pkg.instantiate() reads Manifest.toml and installs exactly the versions it lists. Without a Manifest.toml present, Pkg.instantiate() falls back to resolving from Project.toml alone, which can pick different versions than the ones originally used if any dependency has released a new version since. Committing both files to version control, not Project.toml alone, is what preserves reproducibility.

4.3 Two ends of one mechanism

Nothing above forces a choice between “global” and “per-project.” Both use the identical Project.toml/Manifest.toml mechanism; they differ only in where that pair lives and how many separate pairs are kept. In practice, Julia users tend toward one of 2 recognizable patterns.

4.3.1 The data-science approach: one shared environment

Install packages once, into the default global environment (or a small number of general-purpose environments), and use them across all work without activating anything project-specific.

julia> using Pkg

julia> Pkg.add(["DataFrames", "CSV", "CairoMakie"])

No --project flag, no per-analysis Project.toml. Every session starts with the same packages already available.

Why this is attractive:

  • There is no setup step before starting a new analysis; a package that is already installed is simply there.
  • It matches an interactive, exploratory workflow — a notebook, a REPL session, a quick script — where the goal is an answer, not a shareable artifact.
  • There is one thing to keep track of, not one thing per project.

The costs:

  • No reproducibility. Nothing records which package versions produced a given result. Months later, an updated package can change behavior, and there is no manifest to reconstruct the original state.
  • No isolation. Unrelated pieces of work share one set of installed versions. Upgrading a package for one analysis can silently change behavior in another.
  • Silent drift. The global environment accumulates packages over time, with no record of why any particular one is there.

When it is the right call:

  • Early learning, while the environment mechanism itself is not yet the point of the exercise.
  • Quick calculations, one-off exploration, and throwaway scripts that will not be run again or handed to anyone else.
  • Interactive data exploration where the analysis, not the environment, is what gets saved.

4.3.2 The developer approach: one environment per project

Give each project, package, or assignment its own directory with its own Project.toml and Manifest.toml, activated explicitly before any package is installed or used.

$ mkdir population-model && cd population-model
$ julia --project=. -e 'using Pkg; Pkg.add(["DataFrames", "CairoMakie"])'

or, from an already-running Julia session:

julia> using Pkg

julia> Pkg.activate("population-model")

julia> Pkg.add(["DataFrames", "CairoMakie"])

Every later session that needs the same packages activates the same project:

$ julia --project=. run_model.jl

Why this is worth the extra step:

  • Reproducibility. Manifest.toml pins exact versions. Pkg.instantiate() recreates them on another machine, or on the same machine much later.
  • Isolation. Adding or upgrading a package for one project cannot change behavior in another.
  • Shareability. Committing Project.toml and Manifest.toml alongside the code lets a collaborator, a grader, or a future reader run the same code against the same dependencies.
  • An explicit dependency list. Project.toml states, in one place, everything the project actually needs.

The costs:

  • Setup overhead: a project needs to be created and activated before it does anything useful.
  • More files and more state to track — remembering which project is active, and activating the right one, is a step that can be forgotten.
  • Forgetting to activate the intended project is a common source of confusion: code that runs against the global environment can fail once run with a --project=. that was never given the package, or the reverse.

When it is the right call:

  • Any code that will be handed in, published, shared, or run again after the current session ends.
  • Julia packages under development.
  • Research code, course assignments, and analyses whose exact results need to be reconstructible later.

4.4 Comparing the 2 approaches

Shared global environment Per-project environment
Setup cost None — packages are installed once. One activate (and eventually instantiate) per project.
Reproducibility None; package versions can change under a script without warning. Exact, via Manifest.toml.
Isolation between projects None; all work shares one set of versions. Complete; each project has its own versions.
Shareable with a collaborator Not directly — versions are recorded nowhere. Yes — commit Project.toml and Manifest.toml.
Best fit Learning, quick calculations, one-off exploration. Assignments, packages, research code, anything reused or shared.

4.5 A practical recommendation

These are ends of a spectrum, not a binary choice, and most working practice sits somewhere in between. A reasonable path through that spectrum:

  1. If the environment mechanism itself is not yet the point of the exercise, do not worry about it yet. The “one global environment for everything” approach is a fine place to start.
  2. When ready to be more deliberate, keep the true default global environment clean rather than letting every package ever tried accumulate there. Create one general-purpose environment to act as a personal scratchpad/calculator for casual, everyday work, and use that instead.
  3. Create a dedicated project environment for anything that is a package, a course assignment, or a piece of research code — anything whose results, or whose code, need to still work correctly later or on another machine.

The underlying rule is the same in every case: the less a piece of work depends on being reproduced exactly, the more acceptable a shared environment is; the more it depends on being reproduced exactly, the more a dedicated project environment earns its overhead.

4.7 Common pitfalls

Symptom Likely cause First check
ArgumentError: Package ... not found The package is not available in the active environment. Check the pkg> prompt or Base.active_project() to see which environment is active.
A script works interactively but fails with julia script.jl The REPL had a different environment active than the one the shell command used. Re-run with the intended --project= flag explicitly.
A collaborator’s Pkg.instantiate() installs different versions Manifest.toml was not committed, only Project.toml. Confirm both files are tracked in version control.
Pkg.activate(".") “worked” but no Project.toml appears Activating an empty directory writes nothing until a package is added. Run Pkg.add for at least one package, then check again.
A once-working script now behaves differently The global environment’s packages were updated since the script was last run, and nothing pinned their versions. Consider moving the script into a project environment with its own Manifest.toml.
